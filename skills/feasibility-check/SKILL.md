# Feasibility Check Skill

アプリ実装の実現可能性を**事実ベース**で調査し、技術詳細に踏み込みすぎない回答を返す。

## 発動条件

以下のような問いで自動発動:
- 「〜は実装可能?」「〜できる?」「〜は可能か」
- 「フィジビリティを調べて」「実現可能性を確認」
- 「<API/SDK/サービス>で<機能>はできる?」
- 「<プラットフォーム>で<やりたいこと>は実現できる?」

## 既存設定との関係

- **research skill（@~/.claude/skills/research/SKILL.md）**: 一般的な技術調査。本skillは「実現可否の判定」に特化。
- **Phase 0-5（@context/workflow-rules.md）**: 独立。フィジビリティ調査は実装前の判断材料を提供する単発タスク。
- **最優先指示（@~/.claude/CLAUDE.md）**: 推測禁止を厳守。

## ワークフロー

### Step 1: 問いの明確化

ユーザーの質問から以下を抽出:
- **対象**: プラットフォーム / API / SDK / ライブラリ
- **やりたいこと**: 具体的な機能・挙動
- **制約**: OS、バージョン、料金、その他

不明確ならAskUserQuestionで確認。**勝手に解釈しない**。

### Step 2: 調査ツール選択

優先順位:

1. **devin MCP（最優先）**
   - `mcp__devin__*` 系ツールが利用可能か確認
   - 利用可能なら `ask devin` 相当のツールで質問
   - devinは公式ドキュメント・実装例を横断検索できるため、フィジビリティ調査に最適
2. **context7 MCP** - 公式ドキュメント参照
3. **WebSearch / WebFetch** - 公式ドキュメント・公式ブログのみを参照

**禁止:**
- 個人ブログ・古い情報・Stack Overflowの未検証回答に依拠した断定
- 「たぶん」「おそらく」「〜のはず」での回答

### Step 3: 事実の収集

各主張について以下を確保:
- **一次情報のソース**（公式ドキュメントURL、公式SDKリファレンス）
- **バージョン**（いつ時点の情報か）
- **確認した挙動**（ドキュメント記載 / サンプル実装の存在 / 制約事項）

不明な点は「不明」と明示する。埋めない。

### Step 4: 回答の組み立て

**回答フォーマット:**

```markdown
## 結論

[可能 / 不可能 / 条件付きで可能 / 不明 のいずれか1語で開始]

[1-2文の要約]

## 根拠

- [事実1]（出典: <URL>）
- [事実2]（出典: <URL>）

## 制約・注意点

- [料金、レート制限、プラットフォーム制限など]

## 不明な点

- [調査しても確証が得られなかった項目]
```

**回答レベル感の原則:**
- 技術用語の濫用を避ける
- 内部実装の詳細には踏み込まない
- 「できる/できない」「いくら/いつまで」など、判断に必要な情報に絞る
- コードサンプルは求められた時のみ提示

### Step 5: 不確実性の取り扱い

- 結論が出ない場合は **「不明」** と回答
- 「条件付きで可能」の場合は条件を明示
- 推測で穴を埋めない

## 禁止事項

- devin MCPが使えるのに使わずWebSearchへ即フォールバックすること
- 一次情報なしでの「可能」「不可能」の断定
- 推測表現（「たぶん」「おそらく」「〜のはず」）の使用
- 求められていない実装方法・コード例の提示
- 技術詳細の過剰な説明
